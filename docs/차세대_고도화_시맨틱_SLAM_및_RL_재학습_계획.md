## 1. 왜 기존 알고리즘을 바꾸려 하는가?

현재 `disaster_recovery_ws`(Phase 2-B)는 15가지 재난 시나리오 150회 테스트에서 **99.33%(149/150) 복귀**를 달성했다. 하지만 실제로 굴려 보면 다음 3가지 아쉬움이 남아 있다.

1. **카메라 AI의 결과가 지도에 남지 않는다**
   - 지금 `host_ai_pipeline.py`는 조난자(`person`)를 찾으면 화면에 네모 박스를 띄우고 경고 문자열만 보낸다.
   - 관제자가 **"그래서 조난자나 위험물이 지도상 정확히 어느 방, 몇 m 지점에 있는지"** 지도(`/map`) 위에서 한눈에 볼 수 없다.
2. **라이다 높이(약 17 cm) 아래 장애물은 부딪혀 봐야 안다**
   - TurtleBot3 Burger의 2D 라이다(LDS-01)는 바닥에서 약 17 cm 높이만 수평으로 훑는다.
   - 그보다 낮은 잔해나 턱은 라이다에 안 찍히기 때문에, 지금은 **일단 부딪혀서 멈춘 뒤("어? 안 나가네?") 뒤로 빠져나오는 방식**으로 대처하고 있다.
3. **가스 위험 구역이나 조난자 주변을 미리 돌아가지 못한다**
   - 물리적인 벽이 아닌 "가스 누출 지점"이나 "조난자 바로 앞"은 라이다로 막혀 보이지 않으므로, 강화학습 제어기가 알아서 조심스럽게 비켜 갈 근거가 없다.

## 2. 참고한 논문은 무엇이며, 핵심은 무엇인가?

- **논문**: 이은원 · 김진현 (2025), *「장애물 정보를 포함한 SLAM 기반 실시간 환경 맵핑 알고리즘의 개발 및 구현」*, 로봇학회 논문지 20(2), 245–251.

이 논문이 하는 일은 생각보다 단순하다. **3D SLAM처럼 무거운 작업을 하지 않고, 가벼운 2D 지도 위에 카메라로 본 물체 이름과 위치만 콕콕 찍어주는 것**이다.

```text
[1단계] 카메라로 물체 찾기 (YOLO)
   └─▶ "화면 가운데 의자(Chair)가 보인다!"

[2단계] 거리·방향 계산해서 지도 좌표로 바꾸기
   └─▶ "로봇 위치에서 앞쪽 1.5 m 지점이니까, 지도에서는 (x=3.2, y=1.4)다!"

[3단계] 진짜 있는 물체만 걸러서 지도에 표시·저장하기
   ├─▶ 한 번 깜빡 잘못 본 건 버리고, 여러 번 연속 확인된 것만 '영구 마커'로 확정한다.
   └─▶ 최종 2D 지도 이미지 위에 동그라미와 이름(Chair, Person 등)을 그려 저장한다.
```

## 3. 우리 프로젝트에 어떻게 맞춰 적용할 것인가?

### 3.1 핵심 차이: 우리 로봇에는 3D 깊이 카메라가 없다
논문에서는 거리를 재기 위해 **3D Depth 카메라**를 썼다. 하지만 우리 TurtleBot3 Burger에는 **일반 단안 카메라(RGB)**와 **2D 라이다(LDS-01)**만 달려 있다.

대신 우리에게는 이미 **라이다가 매 순간 정확하게 재는 거리 정보(`/scan`)**가 있다.

| 구분 | 논문 원래 방식 | 우리 프로젝트 적용 방식 (하드웨어 추가 없음) |
| :--- | :--- | :--- |
| **거리 측정** | 3D Depth 카메라로 픽셀별 거리 측정 | **카메라 네모 박스 안에 들어온 2D 라이다 점들의 거리**를 가져다 쓴다. (라이다 높이 밖 물체는 바닥 지면과의 교점으로 대략 추정) |
| **지도에 찍을 대상** | 실내 가구 10종 (의자, 테이블 등) | **조난자(`person`) + 낮은 장애물 + 가스 위험 지점(`/gas/level`) + 구조 요청 위치(`/disaster/audio_alert`)** |
| **실행 위치** | 로봇/PC 통합 ROS 노드 | **Host PC 관제 레이어(`semantic_map_node`)** 에서만 실행한다. (통신이 끊겨도 RPi 4의 단독 자율 복귀 기능은 절대 건드리지 않는다) |

### 3.2 기존 구조에 추가될 흐름
1. **`host_ai_pipeline.py` (소폭 수정)**: YOLO가 찾은 물체의 박스 위치와 **사진이 찍힌 정확한 시간(`stamp`)**을 함께 보낸다.
2. **`semantic_map_node.py` (신규 추가)**:
   - 카메라 박스 + 라이다 거리 + 로봇 위치(TF)를 합쳐 물체의 지도 좌표를 계산한다.
   - 논문 방식대로 **여러 번(예: 5회 이상) 같은 자리에서 확인된 물체만 영구 마커로 확정**한다. (일회성 오탐 방지)
   - 가스 경보나 구조 목소리가 들린 로봇 위치도 같은 지도 위에 마커로 찍어준다.
   - 탐사가 끝나면 **마커가 그려진 2D 지도 이미지(`.png`)와 좌표 목록(`.json`)**을 저장한다.

## 4. 강화학습(Phase 3)은 어떻게 다시 학습할 것인가?

지도에 장애물과 위험 지점을 찍는 것에서 끝내지 않고, **로봇의 복귀 주행 두뇌(RL 모델)가 이 정보를 보고 알아서 피해 가도록** Phase 3 재학습을 진행할 예정이다.

### 4.1 무엇이 달라지나?: 로봇에게 주는 '미니 지도'를 1장 → 3장으로 확장

기존 강화학습 모델(`ContextRLStudent`)은 로봇 주변 `1.8 m × 1.8 m` 영역을 `12 × 12` 격자로 쪼갠 **미니 지도 1장(라이다 장애물)**만 보고 운전했다.
이번에는 같은 크기의 미니 지도를 **3장(3채널)** 겹쳐서 입력으로 준다.

| 미니 지도 | 담기는 정보 | 로봇이 배우게 될 행동 |
| :---: | :--- | :--- |
| **1번 장** *(기존)* | **2D 라이다 벽·기둥** | 기존처럼 벽, 붕괴 기둥, 움직이는 낙석 피하기 |
| **2번 장** *(신규)* | **라이다에 안 보이는 낮은 장애물** | 부딪히기 전에 미리 발견해서 부드럽게 돌아가기 |
| **3번 장** *(신규)* | **가스 위험 구역 · 조난자 보호 구역** | 가스가 새는 곳이나 조난자 바로 앞은 큰 반경으로 우회하기 |

### 4.2 절대 놓치면 안 되는 핵심 안전장치 3가지

1. **통신이 끊겼을 때도 100% 작동해야 한다 (Modality Dropout 훈련)**
   - 재난 현장에서 통신이 끊기면 Host PC가 새 마커를 보내줄 수 없다.
   - 통신이 끊기기 직전까지 받은 마커는 라즈베리파이 메모리에 저장해 두고 계속 쓰되, **학습할 때 전체 훈련의 약 25~30%는 2·3번 장을 일부러 텅 빈 상태(0)로 주고 훈련**한다.
   - 이렇게 하면 통신이 끊기거나 카메라가 가려져도 기존 Phase 2-B처럼 **1번 장(라이다)만 가지고 문제없이 99% 수준으로 복귀**할 수 있다.
2. **가짜 정보(오탐)·위치 오차에도 끄떡없게 훈련한다**
   - 카메라+라이다로 추정한 좌표는 실제 위치와 몇 cm~20 cm 정도 어긋날 수 있고, 가끔 엉뚱한 곳에 가짜 마커가 뜰 수도 있다.
   - 따라서 시뮬레이터에서 마커 위치에 **일부러 흔들림(노이즈), 등록 지연, 미탐지, 가짜 마커**를 섞어서 훈련시킨다. (단, 가짜 마커 때문에 길이 아예 막혀 멈춰 서지 않도록 설계)
3. **처음부터 다시 가르치지 않고, 기존 Phase 2-B 모델을 이어서 학습한다 (Warm-Start)**
   - 이미 수천만 스텝을 학습한 Phase 2-B Teacher 가중치를 그대로 불러온 뒤, 새로 추가된 2·3번 장 연결 부위만 `0` 근처에서 조심스럽게 학습을 시작한다.
   - 기존 주행 실력을 까먹지 않으면서 새로운 회피 능력만 빠르게 덧입힐 수 있고, 기존 `.onnx` 파일은 그대로 두고 **`*_semantic_v3.onnx`라는 새 파일로 분리 저장**해 언제든 안전하게 켜고 끌 수 있다.

## 6. 구현 시 꼭 챙겨야 할 주의사항 3가지

1. **카메라 회전 방향 주의**: 실물 TurtleBot3의 카메라는 옆으로 누워 있어서 코드에서 270° 회전해서 본다. 라이다 점과 짝을 맞출 때 이 회전 각도를 거꾸로 되돌려 계산하지 않으면 왼쪽 물체를 오른쪽에 찍는 실수가 난다.
2. **라이다 거리 한계(3.5 m) 인정하기**: LDS-01은 최대 3.5 m까지만 정확하다. 그보다 멀리서 카메라가 조난자를 보면 먼저 관제 화면 경보만 띄우고, 지도 위 정밀 마커는 로봇이 3.5 m 안으로 다가갔을 때 확정하는 편이 정확하다.
3. **온보드 안전 원칙 지키기**: 시맨틱 지도 생성과 카메라 AI는 무거우므로 반드시 **Host PC**에서만 돌린다. 라즈베리파이 4는 가벼운 마커 좌표 목록과 기존 온보드 복귀 제어만 담당해야 통신 단절 생존성이 유지된다.
